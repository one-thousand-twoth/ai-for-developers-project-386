# Релизы

Релизами управляет [release-please](https://github.com/googleapis/release-please-action).
Отдельный workflow `.github/workflows/release-please.yml` запускается при push
в `main`, в том числе после merge pull request. Его также можно запустить вручную
через Actions → Release Please → Run workflow, выбрав `main`.

## Настройка GitHub

После добавления файлов в `main` откройте Settings → Actions → General →
Workflow permissions и включите **Allow GitHub Actions to create and approve
pull requests**. Если настройка заблокирована, её должен разрешить администратор
организации. Workflow сам запрашивает права записи для содержимого, issues и PR.
Дополнительный секрет для базового сценария не нужен: используется `GITHUB_TOKEN`.

## Обычный цикл

1. Создайте PR с изменениями. Используйте Conventional Commits для сообщений
   коммитов, попадающих в `main`. При **Squash and merge** таким сообщением
   становится заголовок squash-коммита: проверьте его перед слиянием.
2. После merge release-please создаст или обновит release PR с новой версией
   и `CHANGELOG.md`. Несколько изменений собираются в один открытый release PR.
3. Когда готовы выпустить версию, проверьте release PR и слейте его в `main`.
4. Следующий запуск workflow создаст тег вида `v0.1.0` и GitHub Release
   с описанием изменений. Манифест версии обновляется автоматически в release PR.

Первый релиз настроен на `0.1.0`. Далее версия определяется по коммитам:

| Пример | Изменение версии |
| --- | --- |
| `fix: исправить проверку времени` | patch: `0.1.0` → `0.1.1` |
| `feat: добавить бронирование` | minor: `0.1.0` → `0.2.0` |
| `feat!: изменить API бронирования` | до `1.0.0` — minor, начиная с `1.0.0` — major |
| `docs: обновить инструкцию`, `chore: обновить инструменты` | сами по себе не создают release PR |

Несовместимое изменение также можно обозначить строкой `BREAKING CHANGE: ...`
в теле коммита. Если после настройки есть только `chore` или `docs`, отсутствие
release PR ожидаемо: добавьте реальное изменение с `feat` или `fix`.

## Проверки release PR

PR и теги, созданные стандартным `GITHUB_TOKEN`, не запускают другие workflow
автоматически. Обычные PR продолжают проходить Go checks; для автоматических
проверок самого release PR потребуется GitHub App token или PAT.
Если это нужно, создайте секрет `RELEASE_PLEASE_TOKEN` с правами на содержимое,
issues и pull requests репозитория и добавьте в `with` шага release-please:

```yaml
token: ${{ secrets.RELEASE_PLEASE_TOKEN }}
```

При обязательных проверках ветки настройте такой токен до слияния release PR.
Релиз публикует тег и описание; сборка и загрузка бинарников в GitHub Release
этим workflow не выполняются. Версия Go в `go.mod` и mise не является версией
приложения и при релизе не меняется.

Конфигурация: `release-please-config.json`; учёт выпущенной версии:
`.release-please-manifest.json`. После начала релизов манифест вручную менять
не требуется.
